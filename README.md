# TelegramFonts

TelegramFonts is a Telegram-based font ordering and fulfillment system. A Cloudflare Worker owns the public control plane and durable state, while a private Samsung Galaxy A23 performs expensive raster observation and font reconstruction without exposing inbound services.

Core principles:

- Cloudflare D1 is the canonical source of truth.
- Payment, queue, job, artifact, and delivery effects are idempotent and fail closed.
- The A23 is outbound-only and has no direct D1, R2, Telegram, or payment credentials.
- Only the exact generated bytes that pass the required fidelity gates may be published.

## Current project state

The merged system includes the Telegram/SePay control plane, durable jobs and outbox, private R2 delivery, the A23 runner, browser observation storage, reconstruction components, fidelity evidence producers, and durable final-font archiving.

Stage 9D is the current open release gate. PR #72 proposes runner-level publishability and attested archive reuse, but it is **not merge-ready** because the authentic unseen-family device proof has not passed.

                                          │

                                          │

### Responsibilities and trust boundaries

| Component | Responsibility | Must not do |
| --- | --- | --- |
| Telegram client | User interaction, selections, payment instructions, status, delivery | Decide payment or job truth |
| Cloudflare Worker | Public ingress, validation, D1 transitions, outbox, private artifact ingress and delivery | Perform heavy reconstruction |
| D1 | Orders, payments, jobs, leases, outbox, catalogs, sessions, receipts, metadata | Store secrets or large binaries |
| Cloudflare Queue | At-least-once `JOB_READY` transport | Act as canonical job state |
| R2 | Private ZIP storage | Expose a public bucket/domain |
| A23 agent | Browser observation, reconstruction, validation, packaging, upload | Accept public inbound traffic or hold payment/delivery authority |
| Final-font archive | Immutable verified TTF/OTF reuse by exact identity | Treat legacy, corrupt, or mismatched entries as hits |

## End-user workflow

```text
/muahang
  → choose product mode
  → submit an authorized reference URL
  → discover family and styles
  → select styles
  → select TTF and/or OTF
  → confirm order
  → receive bank transfer details and QR
  → pay exact amount with the payment code
  → SePay confirms the incoming transaction
  → A23 reconstructs or reuses verified archived fonts
  → Worker sends ZIP part(s) in Telegram
```

The durable product contract defines:

- `ORIGINAL`: source-observed reconstruction, 5,000 VND per style.
- `VIETNAMESE`: original reconstruction plus bounded Vietnamese audit/extension, 8,000 VND per style.

The Vietnamese branch is a target capability. It must preserve all observed Vietnamese behavior and synthesize only missing behavior. It may not overwrite observed glyphs or measured typography truth.

## Telegram checkout state machine

Telegram interaction state is stored in D1 and protected by workflow tokens, checkout tokens, update ledgers, and optimistic version checks.

```text
IDLE
  → AWAITING_CATALOG
  → SELECTING_STYLES
  → SELECTING_FORMATS
  → CONFIRMING
  → ORDER_CREATED
```

Properties:

- Telegram update IDs are durably deduplicated.
- Catalog results are persisted before selection.
- Style IDs and prices are validated against the persisted catalog, not callback payloads.
- Order creation is an atomic D1 batch bound to the current session version and checkout token.
- Repeated confirmation resolves to the same order.
- Only `TTF` and `OTF` are supported; WOFF and WOFF2 are retired.

## Payment workflow: VietQR display, SePay settlement

The payment architecture remains SePay-based.

```text
Order created in D1
  → Worker generates a unique payment code
  → Telegram displays bank details and a VietQR image URL
  → User transfers the exact VND amount and payment code
  → SePay sends a signed balance-change webhook
  → Worker authenticates and validates the transaction
  → Atomic D1 batch creates payment + job + JOB_READY outbox
  → Order becomes PAID
```

`edge/src/utils/vietqr.ts` only creates the QR image URL from configured bank data, amount, and payment code. It is not the settlement authority. There is no VietQR callback/token integration in the current architecture.

The SePay webhook is accepted only when:

- the webhook secret is configured;
- HMAC-SHA256 signature and signed timestamp are valid;
- the transaction is incoming;
- the receiving account exactly matches configuration;
- exactly one valid application payment code is resolved;
- currency is VND and the amount exactly matches the order;
- the order is still `AWAITING_PAYMENT`;
- the provider transaction ID has not already been processed.

The financial batch atomically:

1. Inserts one verified payment.
2. Inserts one fulfillment job.
3. Inserts one `JOB_READY` outbox event.
4. Changes the order from `AWAITING_PAYMENT` to `PAID`.

No partial payment transition is accepted.

## Durable fulfillment workflow

### State machines

```text
Order:
AWAITING_PAYMENT → PAID → PROCESSING → COMPLETED
        │                    │
        └──────────────→ CANCELLED / FAILED

Fulfillment job:
PENDING → PROCESSING → COMPLETED
             │
             ├──→ RETRY → PROCESSING
             └──→ FAILED

Outbox event:
PENDING → SENT
   │
   └── bounded retry/backoff → FAILED
```

### Transactional outbox

The Worker records durable intent before sending external effects.

- `JOB_READY` is dispatched to the Cloudflare fulfillment Queue.
- `DELIVERY_READY` sends verified private R2 ZIP part(s) through Telegram `sendDocument`.
- Outbox rows use lease tokens, expiry, attempt counters, and bounded backoff.
- Racing dispatchers cannot both own the same attempt.

### Queue pull and D1 lease fencing

The A23 is an external HTTP-pull Queue consumer:

1. Pull a bounded Queue message batch.
2. Call `POST /internal/jobs/:job_id/claim` using `A23_NODE_SECRET`.
3. D1 performs compare-and-set claim and issues a random lease token.
4. Run a background heartbeat during compute.
5. Bind upload, completion, failure, and retry to the current unexpired lease.
6. ACK Queue only after a durable authoritative outcome.

Queue delivery is at least once. D1 lease fencing—not Queue visibility—is authoritative for duplicate prevention.

## MAX font production pipeline (tiered reuse, binary-first)

The production runner resolves each requested style+format through a fail-closed
reuse order. A tier skips only the work it causally replaces; no caller-authored
PASS value is ever accepted:

```text
L1  exact final artifact (attested archive hit, byte-identical)
L2  canonical FontModel cache (skips acquisition + reconstruction + optimization;
    candidate build + held-out four-consumer gate still run)
L3  durable hash-verified authorized-binary cache + authorized binary
    acquisition (binary-first; zero geometry reconstruction); integrity
    ambiguity is terminal, drift/corruption fails closed
L4  exact completed raster observations (MAX reconstruction path)
L5  authorized browser raster observation (acquisition)
```

Successful authorized raster-provider results are never discarded: they are
converted into complete immutable exact-tuple observations (rasters, metrics,
pairs, features), finalized with the same strict schedule checks as direct
browser collection, and then feed the normal Stage 9D raster gate.

Authorized binary artifacts pass the same closed artifact-bound four-consumer
production boundary (FontTools, FreeType, HarfBuzz, real headless Chromium);
no capability is injectable, and capability absence or forged evidence fails
closed.

Final identity binds source/reference fingerprint, family/style, ORIGINAL|VIETNAMESE,
TTF|OTF, coverage, pipeline/build version, and Vietnamese/AI provenance. Raster
identity additionally binds the exact browser/config tuple. Cache or artifact
corruption, stale versions, ambiguous identity, or failed provenance are misses.

```text
Authorized reference URL
  → catalog/style discovery (pre-payment: catalog only)
  → verified settlement gate
  → tiered reuse resolution (L1→L5)
  → authorized acquisition order:
      native Chrome --headless=new --dump-dom (primary)
      → authorized persistent Chrome/session (fallback)
      → authorized provider raster endpoint (fallback)
  → valid authorized binary wins: verify bytes/type/family/style/provenance,
    convert/build requested TTF/OTF only, four-consumer validation
  → otherwise raster observation:
      lossless raster + metrics + pairs + features
      → immutable completed snapshot
      → fit/held-out partition
      → calibration → SDF/coverage → topology → Bézier fitting
      → fit-only deterministic optimization
      → canonical FontModel
      → Vietnamese extension (VIETNAMESE mode only)
      → TTF/glyf and OTF/CFF build
      → FontTools + FreeType + HarfBuzz + Chromium evidence
      → held-out fidelity evaluation
      → exact artifact attestation
  → immutable attested archive (all items PASS before any archive/package)
  → deterministic package
```

### 1. Source and catalog discovery

Before payment, the Worker performs only URL validation and catalog/style discovery. All cache/acquisition/compute runs after verified settlement.

Reference URLs must be canonicalized and authorized. Automated binary/raster
retrieval operates under written provider authorization covering the approved
MyFonts/Monotype workflow; a fallback stage starts only after the preceding
capability proves binary/raster insufficiency, and every retrieval is bounded.
Unapproved internal CDN enumeration, anti-bot bypass, stealth/fingerprint
masking, and forged request identity remain outside the architecture.
Authorization documents, credentials, cookies, and session material are never
requested, published, committed, logged, or embedded in artifacts; provider
adapters are injectable and testable without real credentials.

### 2. Browser observation

The measurement layer launches an installed native Chromium/Chrome binary with:

- the modern native headless engine;
- an isolated temporary profile;
- a loopback-only CDP endpoint;
- no proxy inheritance;
- explicit startup, endpoint, handshake, and cleanup validation.

The session records:

- lossless PNG glyph rasters;
- multiple resolutions;
- deterministic base, adaptive, and held-out subpixel phases;
- direct canvas metrics;
- pair advances and kerning evidence;
- configured OpenType feature probes;
- browser version and observation configuration hash.

Loading HTML alone is not evidence. The pipeline requires an actual selected font face, raster bytes, measurements, and typography observations.

### 3. Durable observation identity

Every observation is bound to:

```text
(reference_id, style_id, browser_version, config_hash)
```

Completion requires exact equality across declared coverage, raster schedule, pair schedule, and feature probes. Incomplete, extra, stale, mixed, or cross-environment observations fail closed.

Raster files and reconstruction caches are cryptographically namespaced. Paths are resolved and containment-checked before reads to prevent traversal or cross-run aliasing.

### 4. Reconstruction

Only the fit partition may affect reconstruction:

- renderer calibration maps pixels to font units;
- signed-distance/coverage data stabilizes contour recovery;
- topology separates outer contours and holes;
- line and cubic Bézier segments form outlines;
- bounded deterministic optimization improves fit evidence only;
- direct browser measurements determine metrics;
- pair and feature evidence derives kerning/OpenType behavior;
- results assemble into a canonical `FontModel`.

Held-out rasters, pairs, fingerprints, and consumer results must never influence fitting, candidate selection, stopping, or retry.

### 5. Optional Vietnamese extension

The Vietnamese branch runs after the canonical model exists:

- preserve every observed Vietnamese glyph and behavior;
- audit NFC/NFD and composition coverage;
- synthesize only missing glyphs from measured components;
- preserve measured metrics and OpenType truth;
- validate `ccmp`, `mark`, `mkmk`, collisions, clipping, spacing, and corpus behavior;
- for missing coverage only, the bounded Woku-primary cascade may generate
  candidates under fixed routing: Woku base `https://llm.wokushop.com/v1`
  exact model `gpt-5.6-luna` PRIMARY, then exact model `gemini-3.7-flash`
  FALLBACK (each attempted at most once); if Woku is unavailable, invalid, or
  deterministically rejected, the existing OpenRouter route is used unchanged
  as the downstream fallback: PRIMARY `google/gemma-3-12b-it` for every case,
  DIFFICULT `google/gemma-3-27b-it` only on deterministic escalation, and a
  rare ARBITER `google/gemini-3.1-flash-lite` at most once after an
  unresolved deterministic disagreement; no other model or substitution, no
  retry loops, no schema/validator bypass. Exact hits and
  complete-source/ORIGINAL paths make zero calls. The extension binds
  provider/model/route/fallback-reason/prompt/schema/config/source/target
  provenance identities into immutable provenance. ORIGINAL mode never
  constructs the service. The runtime API keys (key names `wokushop_api_key`
  and `openrouter_api_key`) are runtime secrets consumed only at the
  composition boundary; responses are sanitized closed schema only.

AI cannot invent mappings, alter observed glyphs, author PASS, weaken thresholds,
or bypass FontTools/FreeType/HarfBuzz/Chromium/held-out validators. Forged,
non-finite, or incomplete AI output fails closed with no publish/archive.

### 6. Candidate build and four-consumer gate

The builder emits TTF/OTF from the canonical model. The exact file is described by an immutable path, size, and lowercase SHA-256 descriptor.

All four consumers must evaluate that same artifact:

- **FontTools**: direct load, tables, cmap, and metrics.
- **FreeType**: rasterization for every required sample and thresholds.
- **HarfBuzz**: shaping, glyph IDs, clusters, advances, and positions.
- **Chromium**: direct load, fallback rejection, canvas, glyph, and pair evidence.

Evidence types are closed and finite. Missing capability, partial samples, non-finite values, forged aggregates, mismatched fingerprints, or caller-authored PASS fields produce no publishable bundle.

### 7. Stage 9D publish boundary

The target runner release gate requires:

- deterministic fit-only convergence;
- finite, non-increasing accepted objectives;
- independent PASS for every style/format;
- identical bytes across PASS, archive, and package;
- no rebuild after PASS;
- no archive/package/upload/completion on partial PASS;
- immutable Stage 9 attestation for archive reuse;
- legacy, stale, unattested, or tampered entries to become misses.

This boundary remains under review in Issue #71 and PR #72. It is not merged or production-ready until its required proof passes.

## Archive, packaging, upload, and delivery

### Archive hit

A repeat job skips collection/reconstruction only when every requested style/format has a compatible verified archive entry.

### Archive miss

The runner collects or reuses complete observations, reconstructs, builds, validates, and—after the release gate—atomically retains immutable final artifacts.

### Deterministic ZIP

The package manifest binds:

- order and job IDs;
- family, styles, and formats;
- file names, sizes, and SHA-256 hashes;
- package parts when the payload exceeds the configured limit.

### Private upload and completion

1. `PUT /internal/jobs/:job_id/artifact` verifies node auth, lease, size, and SHA while streaming into private R2.
2. `POST /internal/jobs/:job_id/complete` atomically creates the receipt, completes job/order, records artifact metadata, and inserts one `DELIVERY_READY` event.
3. The outbox dispatcher sends every verified R2 part directly to Telegram.
4. Signed `/downloads/:order_id` URLs provide an expiring private retrieval path.

The A23 never receives R2 credentials.

## Failure handling and recovery

The system prefers a safe BLOCKED/FAILED outcome over fallback:

- failed claims do not start compute;
- expired/fenced workers cannot upload or complete;
- unexpected post-claim errors must converge to retry or terminal failure;
- Queue ACK follows durable completion only;
- scratch paths are isolated and containment-checked;
- corrupt archives/caches become misses;
- completed receipts/artifacts cannot be overwritten by stale workers;
- production rescue/rearm requires Human authorization and exact CAS predicates;
- production is never an iterative debugging environment.

## A23 runtime

```text
Android root
  → Termux boot/watchdog and exclusive supervisor lock
  → verified host control scripts
  → clean Debian ARM64 chroot environment
  → pinned Python/runtime dependency identity
  → sequential browser/compute/consumer stages
  → external ext4 immutable archive
```

The supervisor fails closed when release identity, runtime identity, archive mount, browser capability, or exclusive-lock ownership is ambiguous. Host control scripts and worker release payload are separate verified identities.

The current Stage 9D device proof exposed a remaining Chromium readiness problem inside the Debian chroot. That gap is tracked in Issue #71; it does not authorize device mutation, browser-control bypass, or weaker fidelity gates.

## Architect and Executor workflow

GitHub is the durable AI coordination and recovery plane.

```text
Human intent
  → Architect defines outcome, invariants, acceptance, evidence, and gates
  → Architect creates one canonical GitHub contract
  → Human sends one short trigger to the Executor
  → Executor chooses HOW, implements, tests, opens/updates PR, posts evidence
  → Architect reviews actual HEAD/diff/evidence
  → Human performs final merge
```

Roles:

- **Human**: intent, consequential authorization, trigger routing, final merge.
- **Architect**: architecture, contract, acceptance, review, durable project memory.
- **Executor**: implementation HOW, diagnostics, tests, evidence, and PR delivery; never merges.
- **GitHub**: canonical issues, reviews, CI, source, and recovery state.

Canonical states:

```text
READY
  → EXECUTING
  → ARCHITECT_REVIEW
  → FIX_REQUIRED (when needed)
  → ARCHITECT_REVIEW
  → MERGE_READY
  → MERGED
  → COMPLETE
```

Consequential actions require:

```text
HUMAN_AUTH_REQUESTED
  → Human approval
  → exact ARCHITECT | EXECUTING_AUTHORIZED GitHub envelope
  → one bounded execution
  → ARCHITECT_REVIEW
```

Human approval text alone is not executable authority. The active Executor obeys the latest GitHub contract and reports under its assigned executor identity; chat carries only short triggers and terminal markers.

## Non-negotiable boundaries

- SePay remains the settlement provider until a separately approved migration is implemented and verified.
- No anti-bot bypass, stealth session, clearance-cookie reuse, forged request identity, internal-CDN enumeration, or source-font extraction.
- No mock, fixture, manual report, or green CI may substitute for required device/production/four-consumer evidence.
- No held-out evidence may influence optimization.
- No rebuild or artifact substitution after PASS.
- No partial multi-style/multi-format publish.
- No production mutation without Human authorization and an Architect execution envelope.
- No secret in Git, logs, Issues, PRs, chat, artifacts, or tests.
